# devwf CLI implementation plan

Design: `docs/superpowers/specs/2026-11-10-devwf-cli-design.md`

## File layout

- `bin/cli.js` — entry point: shebang, argv in, exit code out. No logic beyond wiring.
- `cli/args.js` — pure argument parser (no fs, no network, no process).
- `cli/monitor-client.js` — the only place that talks HTTP to the monitor.
- `cli/sessions.js` — discovers session state files by key, read-only.
- `cli/commands.js` — the five subcommands, composed from the three modules above.
- `tests/cli-args.test.js`, `tests/cli-monitor-client.test.js`,
  `tests/cli-sessions.test.js`, `tests/cli-commands.test.js`

## Tasks

### Task 1 — Argument parser (TDD)

Write `tests/cli-args.test.js` first.

- `parseArgs(["close", "--session", "abc"])` → `{ command: "close", session: "abc", dryRun: false }`
- `parseArgs(["drop", "--session", "abc", "--reason", "stale"])` → carries both
- `parseArgs([])` → `{ command: "help" }`
- `parseArgs(["--help"])`, `parseArgs(["--version"])` recognised
- unknown flag → throws a `CliError` with a message naming the flag
- unknown subcommand → throws naming the subcommand and listing valid ones
- a flag given twice → last value wins (documented, not silent surprise)

`CliError` lives in `cli/args.js` and carries `exitCode`. `bin/cli.js` catches it.

### Task 2 — Monitor client (TDD)

Write `tests/cli-monitor-client.test.js` with an injected `fetch`.

- missing `DEVWF_MONITOR_URL` → refusal naming the variable
- missing `DEVWF_MONITOR_TOKEN` → refusal naming the variable (never send an
  unauthenticated write)
- `closeSession({ sessionKey })` → `POST `<base>/api/session/close`` with
  `authorization: Bearer <token>` and JSON body; returns parsed body
- `revokeShare({ token })` → `DELETE /api/share?token=<encoded>`
- `revokeOrphans()` → `POST /api/share?revoke-orphans=1`
- `listShares()` → `GET /api/share?all=1`
- `listSessions()` → `GET /api/sessions`
- non-2xx → throws `CliError` carrying the status and the server's error text
- the token is never included in a thrown message or in returned data

### Task 3 — Session discovery (TDD)

Write `tests/cli-sessions.test.js` against a temp `projects/<p>/users/<u>/` tree.

- finds `workflow-state.<key>.json` and returns its path plus parsed state
- key matching zero files → `CliError` "unknown session"
- key matching two files (two user dirs) → `CliError` "ambiguous", listing both
- returns phase and task description for display
- never writes

### Task 4 — Commands (TDD)

Write `tests/cli-commands.test.js` with injected dependencies
(`{ monitor, sessions, handlers, out }`) so no network or real state is touched.

- `close` without `--session` → refusal before any HTTP call
- `drop` without `--reason` → refusal before loading state
- `drop` on unknown session → refusal, no handler call
- `--dry-run` on every writing command → zero writes, output says "would"
- `drop` with a valid target → `handleDropTask` called with `{ reason }` and the
  state loaded from the discovered file
- `complete` validates DoD before doing anything: an open item surfaces the
  handler's refusal text and exits non-zero
- success output is one line per effect, in English

### Task 5 — Entry point

`bin/cli.js`:

```
#!/usr/bin/env node
```

- sets `process.exitCode` from the result, never `process.exit()` mid-write
- `--help` prints usage covering all five subcommands and the two env vars
- `--version` prints `package.json.version`
- any `CliError` prints to stderr, exits with its `exitCode` (default 1)

`package.json`: `bin: { "devwf": "bin/cli.js" }` (keeping `dev-workflow-mcp`).

### Task 6 — README

New `### Closing sessions and cards from the terminal` section under the monitor
material, with runnable examples for all five subcommands, the two environment
variables, the exit-code contract, and the explicit statement that no process is
ever signalled.
